PulseRail · 1.0.0-rc4

From a complete Android project to a traceable build — from the phone.

PulseRail is a phone-side Android application that imports a complete project ZIP, inspects project health, coordinates a private GitHub Actions build, verifies the exact resulting artifact and supports explicit phone or Wear OS delivery. The ambition is not another build button. It is a build path that can explain itself.

Release candidate · owner testing

Build from the phone. Keep the evidence.

Repository, commit, workflow run, attempt, artifact identity, package, version, cryptographic hash and signer are treated as part of the product state. A green build result is evidence, but not the whole verification story.

Why it matters

A successful build can still leave dangerous questions unanswered.

PulseRail is being designed around questions that ordinary build interfaces often leave implicit.

Which source produced this APK?

Artifact verification binds the output back to the repository, exact source revision, workflow run and attempt rather than relying on a filename or a success badge.

Which identity will this app update?

Package identity and signing lineage are treated as update identity. Missing or conflicting signer evidence is a blocker, not an invitation to silently generate a replacement.

Did recovery duplicate the operation?

Upload, dispatch and observation are designed around persisted transaction identity so network loss or process death can reconcile existing work before creating new work.

Was a repair actually authorized?

Safe Build Repair is bound to the exact source, proposal, requirements evidence and ordered change set. A stale checkbox is not mutation authority.

Can untrusted project code reach secrets?

Imported Gradle code is treated as untrusted. Build, verification and signing boundaries are separated so project code does not simply inherit signing authority.

Can the workflow be used non-visually?

Screen-reader operation, meaningful state announcements, focus behavior and explicit next actions are treated as product behavior, not post-release polish.

Engineering principles

Evidence before authority.

The common thread is conservative authority: the system should know why an action is allowed before it performs an action that is difficult to reverse.

Verifiable by design

Important outcomes are tied to explicit identities, hashes, versions and durable state instead of being inferred from appearance or timing.

Fail closed

Uncertain evidence remains uncertain. It does not silently become permission to repair, re-key, install, dispatch again or cross an identity boundary.

Recovery is a normal path

Mobile processes die and networks disappear. Recovery is designed into the transaction model rather than bolted on as a “try again” button.

Security boundaries stay narrow

Credentials, imported source, verification and signing are kept in deliberately different trust zones wherever the workflow permits it.

Accessibility is functional correctness

A state that exists visually but is not communicated to assistive technology is incomplete product state.

Claims follow evidence

Release documentation distinguishes implemented design, deterministic validation, CI evidence and still-pending real-world acceptance instead of collapsing them into one “done” label.

Current status

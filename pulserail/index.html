PulseRail · Android build orchestration

Your Android build should have a chain of custody.

PulseRail is a phone-side workflow for complete Android projects. It inspects what you actually imported, coordinates the build, checks the resulting binary, protects update identity and keeps the path from source to installable artifact explainable.

The idea is simple: a green build badge proves less than most people think. PulseRail is being built so the result can be tied back to the source, the build event, the binary identity and the signer you intended to trust.

Why it is different

It treats the awkward cases as part of the product.

Most build tools optimize for the happy path. PulseRail is being designed around the moments when confidence usually disappears: interrupted operations, uncertain repairs, signer loss, mismatched artifacts, changed targets and projects you should not blindly trust.

Provenance, not just output

The finished binary is checked against the identity of the source and build that produced it, rather than being trusted because its filename looks right.

Recovery without blind repetition

A lost network connection or terminated mobile process should not automatically mean “start again”. PulseRail is designed to recover the same operation when it can be identified safely.

Signing identity is product identity

An existing application cannot be safely “fixed” by silently inventing a new signer. PulseRail treats package, signer and update lineage as boundaries that must remain coherent.

Build Doctor can refuse

Diagnosis and permission are separate. When the evidence is not strong enough for a deterministic repair, the product should explain the problem rather than guess.

Imported projects are not automatically trusted

PulseRail assumes that a project may contain surprising or hostile build behavior. Security-sensitive authority is kept separate from whatever the imported project is allowed to do.

Delivery remains explicit

Phone installation stays in Android’s normal user-driven path. Wear OS delivery is bounded to the selected watch and the verified artifact rather than becoming a general-purpose remote-control feature.

The journey

From project ZIP to something you can justify installing.

The public story can stay short even though the engineering underneath it is not.

01

Import

Bring in one complete Android project and establish what the project actually is before treating it as buildable.

02

Understand

Inspect project health and explain material requirements or blockers before the build path advances.

03

Build

Coordinate a private cloud build while retaining the identity of the operation that the user started.

04

Verify

Check that the received artifact belongs to the expected source, application and signing identity.

05

Deliver

Hand the verified result to the explicit phone or watch installation path without pretending that compilation alone is functional certification.

Build Doctor

The useful part of automation is knowing when not to automate.

Build Doctor is being expanded beyond error-message decoration. Its job is to distinguish what can be established from evidence, what can be repaired mechanically, what needs a guided decision and what should simply stop.

Evidence before mutation

Automatic change is reserved for cases where the product can justify the change against trusted requirements and the current project state.

The original remains meaningful

Repair is treated as a controlled revision of a known source, not an invisible rewrite that makes it impossible to tell what changed.

Protected boundaries stay protected

Application identity, signer identity, security-sensitive behavior and user code are not treated as convenient repair targets.

Success is described precisely

Built, verified, installed and observed running are different claims. PulseRail is designed not to collapse them into one vague “works” state.

Trust model

Confidence comes from boundaries, not optimism.

The public documentation deliberately describes guarantees and user-visible behavior without publishing the internal decision rules, recovery state machine, repair mappings, protocol details or security thresholds that implement them.

Private build path

Projects are built through a private workspace rather than being published as source simply to obtain a cloud build.

No silent re-key

If the expected signing identity is unavailable or contradictory, that is a condition to resolve, not permission to substitute a new identity.

Secret-aware boundaries

Imported project logic is not given automatic access to signing authority merely because it participates in the build.

Release-candidate breadth

The RC4 verification program includes representative phone, Wear OS, Watch Face Format, failure-recovery and adversarial project paths before public release is considered.

PulseRail’s most unusual feature may be the one that is hardest to screenshot: it is being designed to preserve reasons, not only results.

GitHub connection

Moving toward browser-based onboarding.

The RC4 target is a browser-based PulseRail GitHub App connection with a verified return to the Android application. The current Setup Wizard still contains the historical fine-grained PAT-first path, so the site does not present the cutover as finished.

Release status

Interesting enough to show. Not finished enough to ship.

PulseRail 1.0.0-rc4 remains under active integration, deterministic validation and owner testing. Whole-product coherence, final onboarding, release documentation and exact-candidate verification still stand between this preview and a public release.

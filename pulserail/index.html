PulseRail · Android build orchestration

Your Android build should have a chain of custody.

PulseRail turns a complete Android project ZIP into a controlled, traceable build workflow from the phone: inspect the project, coordinate the exact cloud build, verify the resulting artifact, preserve signing identity and deliver only what can be tied back to its evidence.

The difference: “workflow succeeded” is not the final answer. PulseRail keeps track of which source, which run, which attempt, which artifact, which package, which version and which signer produced the file you are about to trust.

Complete workflow

One project. One explainable transaction.

The workflow is built to preserve source and transaction identity through import, inspection, repair, dispatch, remote observation, verification and delivery.

Accept one complete Android project ZIP and validate its structure before it becomes the active project.

02

Determine the actual project root, project health and relevant build requirements.

03

Repair when justified

07

Deliver

Preserve identity

When an existing application requires its original signer, recovery is treated as identity restoration rather than silent replacement.

Build Doctor

Diagnosis is not permission.

Build Doctor separates project-health findings, requirements, deterministic safe repair and guided intervention. Uncertain evidence remains diagnostic instead of automatically becoming authority to modify a project.

Requirements have meaning

A requirement may be a minimum, maximum, exact version, range, supported set, inventory, checksum, boolean rule or advisory. A minimum is not silently treated as an exact version.

Fresh evidence matters

Requirements are resolved from trusted official sources. Stale, conflicting or unsupported evidence can inform diagnosis but cannot authorize deterministic repair.

Repair preserves the original

Safe repairs create bounded copy-on-write revisions, apply exact changes, re-inspect the output and stop when protected invariants no longer match.

Identity is protected

Application identity, signing lineage and other protected project boundaries are not silently rewritten for convenience.

Artifact provenance

“This APK came from that project” becomes a testable statement.

PulseRail’s verification model connects the binary to multiple independent identities rather than trusting a filename or a single green status.

Source identity

Repository, branch and exact commit SHA establish what source was intended to build.

Run identity

Workflow run, attempt and dispatch identity distinguish the original operation from a rerun or replacement.

Artifact identity

Artifact ID, package, version, SHA-256 and signing certificate identify the binary that was actually received.

A filename can be copied. A success badge can describe the wrong attempt. Provenance is stronger when several independent identities have to agree.

Delivery

Verified source. Explicit target.

Phone

A verified APK is exported to Android Downloads. The user explicitly starts the operating system’s normal installation flow; updates still depend on matching application identity and signer.

Wear OS

The watch path checks the verified artifact, selected authenticated watch, package/version/signing identity, available space and installation state before a scoped installation operation.

GitHub connection

Moving toward browser-based onboarding.

The RC4 target is a PulseRail GitHub App browser flow with a verified return to the Android application. The security and broker policy boundaries for that model exist in the current source.

Current limitation: the Setup Wizard still contains the historical fine-grained PAT-first product path. Completing the GitHub App product cutover remains an explicit RC4 acceptance blocker, so this site does not claim the migration is finished.

Release status

Interesting enough to show. Not finished enough to ship.

Final acceptance still requires whole-product coherence, complete source/documentation parity, completion of the GitHub App onboarding cutover and final exact-head release verification. A successful build alone is not represented as functional certification.

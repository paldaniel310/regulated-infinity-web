PulseRail · Android 构建编排

Android 构建也应该有可验证的来源链。

PulseRail 是一个从手机端运行的完整 Android 项目工作流。它先确认你实际导入了什么，再协调构建、检查得到的二进制文件、保护更新身份，并让从源代码到可安装产物的路径保持可解释。

核心想法很简单：绿色的 build 状态没有人们想象中那么有证明力。PulseRail 的目标是让结果能够回溯到源、构建事件、二进制身份以及你原本信任的签名身份。

为什么不同

棘手情况也是产品的一部分。

很多构建工具只优化顺利流程。PulseRail 也为那些通常最容易失去确定性的时刻而设计：操作中断、修复依据不足、签名身份丢失、产物不匹配、目标发生变化，或者导入的项目本身就不应该被自动信任。

重视来源，而不只是结果

最终二进制文件必须与产生它的源和构建身份一致，而不是仅仅因为文件名看起来正确就被信任。

恢复，而不是盲目重复

网络断开或移动进程被终止，不应该自动等于“重新开始”。只要原操作的身份还能安全确认，PulseRail 就会优先恢复同一操作。

签名身份就是产品身份

已有应用不能靠悄悄换一个新签名者来“修复”。包身份、签名身份和更新链必须保持一致。

Build Doctor 可以拒绝

诊断与授权是两回事。证据不足以支持确定性修复时，产品应该解释问题，而不是猜测。

导入的项目不会自动被信任

PulseRail 假设构建逻辑可能出现意外甚至恶意行为，因此安全敏感权限不会因为项目参与构建就自动交给它。

交付仍然是明确操作

手机端继续使用由用户明确启动的 Android 正常安装路径。Wear OS 操作则绑定到选定手表和经过验证的产物。

流程

从项目 ZIP 到一个你能解释为什么可以安装的文件。

公开故事可以很简洁，即使背后的工程并不简单。

01

导入

导入一个完整 Android 项目，并先确定系统实际面对的是什么。

02

理解

在继续构建前理解项目状态以及关键要求或阻塞条件。

03

构建

协调私有 cloud build，同时保留用户发起操作的身份。

04

验证

确认收到的产物属于预期源、应用身份和签名身份。

05

交付

将验证后的结果交给明确的安装路径，同时不把“成功编译”夸大成“功能已认证”。

Build Doctor

有价值的自动化，也必须知道什么时候不该自动化。

Build Doctor 的目标是区分：哪些内容可以由证据确认，哪些可以机械性修复，哪些需要引导式决定，以及哪些情况必须直接停止。

先有证据，再做修改

只有当可靠要求和当前项目状态足以支持时，自动修改才有正当依据。

原始源仍然可理解

修复应该是对已知源的受控修订，而不是看不出发生了什么的隐式重写。

受保护边界继续受保护

应用身份、签名身份、安全敏感行为和用户代码不会为了方便而成为自动修复目标。

“成功”需要精确描述

已构建、已验证、已安装、已观察运行是不同的陈述。PulseRail 不会把它们合并成含糊的“能用”。

信任模型

信任来自边界，而不是乐观假设。

公开文档会描述保证与用户可见行为，但不会公开实现这些能力的内部决策规则、恢复状态机、修复映射、协议细节或安全阈值。

私有构建路径

项目可以在私有 workspace 中构建；不需要为了得到 cloud build 而公开源代码。

不会静默更换签名身份

如果预期签名身份缺失或互相冲突，应当解决这个状态，而不是用一个新身份替代它。

敏感权限保持隔离

导入的项目逻辑不会仅仅因为参与构建就自动获得签名权限。

RC4 覆盖范围广

在考虑公开发布前，release candidate 验证计划包含代表性的手机、Wear OS、Watch Face Format、故障恢复以及 adversarial 项目路径。

PulseRail 最特别的功能也许最难用截图展示：它不仅想保留结果，还想保留为什么可以相信这个结果的理由。

GitHub 连接

正在转向浏览器 onboarding。

RC4 的目标是通过浏览器完成 PulseRail GitHub App 连接，并验证返回 Android 应用的过程。当前 Setup Wizard 仍保留历史 fine-grained PAT-first 路径，因此网站不会声称迁移已经完成。
